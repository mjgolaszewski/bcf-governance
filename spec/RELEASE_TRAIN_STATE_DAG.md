# Release Train State and Custody DAG

This specification extends the analysis implemented by PR #339. It is the
prospective review surface for late release-train corrections; it does not
replace the canonical CI graph, lifecycle ledger, authority contract, or
provider evidence.

## Invariants

1. One exact subject means one commit, tree, controller identity, workflow
   authority projection, run, attempt, and proposition at every authenticated
   boundary.
2. A later subject may reuse evidence only when the canonical applicability
   resolver proves the inputs and proposition unchanged. Evidence is never
   relabeled by an operator.
3. Candidate execution cannot authorize itself, publish status, mutate
   protection, install a controller, or publish a release.
4. Every provider mutation follows complete authenticated read-side validation.
   Missing, redacted, ambiguous, stale, or conflicting state fails closed.
5. `inapplicable` is closed and typed: it identifies the exact transition
   class, subject, policy, and alternate governed lane. It never means bypass.
6. Generated bytes, manifests, locks, workflow authority, version identity,
   release tag, and publication inputs are mechanically derived from canonical
   owners. An agent does not transcribe them.
7. Trusted-controller transitions are explicit: ordinary-current,
   pending-rotation, installed-current, or authenticated recovery-reentry.
   Only ordinary-current is release-certifying.
8. Release publication consumes one exact terminal-phase certification and one
   exact release receipt for current main. Bounded workitem certification is
   never release authority.
9. An absent release tag is not an operator task. After all read-side checks,
   the trusted publisher creates the exact annotated unsigned tag, rereads it,
   and rejects every conflicting tag state.
10. Terminal cleanup retires only state and credentials owned by the exact
    execution. No wildcard cleanup, implicit persistence, or global pruning is
    permitted.

## State matrix

| State | Required exact data | Legal next operation | Mechanical rejection |
| --- | --- | --- | --- |
| Authored candidate | base commit/tree, candidate tree, semantic intent | canonical reconcile | dirty or ambiguous owners, context/LOC excess, stale generated bytes |
| Reconciled candidate | definition commit, authority commit when required, clean tree, prospective report | protected PR | incomplete fixed point, authority mismatch, incompatible installed parser |
| Certified PR | head/tree, governance run/attempt, complete producer receipts, PR certification | normal protected merge | missing/wrong producer, subject, session, control, or protection state |
| Merged main | merge commit/tree, protected merge relationship | exact-main admission | non-authoritative main, stale workflow authority, malformed lifecycle intent |
| Pending rotation | main identity, installed N, target N+1, exact provider-built artifact | bootstrap and probe | installed N cannot parse/authorize candidate, artifact mismatch, evidence fan-out |
| Installed current | target equals installed, bootstrap/probe/confirmation custody, no recovery residue | fresh exact-main | runner disagreement, hand-authored pin, incomplete normalization |
| Exact-main certified | current commit/tree, terminal proposition, complete truth/finalizer/publisher identity | release authorization | bounded scope, moved main, incomplete inventory, wrong controller |
| Release authorized | exact certification, controller custody, owner dispatch run/attempt | hosted build | stale subject, candidate authority, copied artifact coordinates |
| Release built | authorization, build manifest, wheelhouse lock, exact assets | independent runtime verification | unlocked input, source drift, build identity mismatch |
| Release verified | build identity, runtime report, exact asset hashes | trusted collection | failed runtime, mismatched run/attempt, unbound asset |
| Release collected | release receipt, certified assets, collector run/attempt, provider digest | trusted publication | receipt not current exact main, wrong assets/controller/role |
| Publication ready, tag absent | immutable releases enabled, short-lived credential present, attestations complete | publisher creates tag and draft | any failed read-side check; tag creation before attestations |
| Publication ready, tag exact | exact annotated unsigned tag to certified commit | publisher creates draft | lightweight, signed, malformed, or wrong-subject tag |
| Publication conflict | any non-exact tag or release state | stop | mutation, deletion, force update, or treating conflict as absence |
| Published custody | immutable non-draft release, exact tag/assets/digests/attestations | credential retirement and adopter qualification | mutable/draft release, missing asset, retained credential |
| Qualified release | immutable custody plus adopter same-byte reports | phase/release closeout | unpublished package, different bytes, simulated adopter authority |

## Construction tree

### Invariants to primitives

- Exact identity
  - commit/tree projection
  - workflow blob and definition-commit projection
  - run/attempt and artifact provider digest
  - evaluation scope, target, and proposition
- Deterministic derivation
  - fixed-point reconciler
  - CI graph compiler and renderer
  - manifest, lock, mirror, and editorial generators
  - provider-state resolver
- Authority separation
  - candidate producer
  - trusted finalizer
  - status publisher
  - release authorizer, builder, verifier, collector, and publisher
- Provider mutation safety
  - immutable-release setting inspection
  - optional exact tag read (`404` means absent only for this GET)
  - annotated tag-object creation
  - non-force tag-reference creation
  - provider reread and exact tag verification
  - draft upload, digest verification, and immutable publication
- Controller lifecycle
  - compatibility classification using installed N
  - provider-built N+1 artifact resolution
  - independent bootstrap and probe
  - confirmation, promotion, normalization, and fresh exact-main

### Primitives to contracts

- `governance/ci-graph.yml` and registered extensions own executable topology,
  environment, role separation, and generated workflows.
- `governance/ci-authority.yml` binds workflow identity and definition commits.
- lifecycle and evaluation-scope contracts select PR progress, bounded workitem,
  phase closure, controller transition, or release proposition.
- release public contracts own version and canonical tag derivation.
- release receipts bind the exact certified subject, assets, controller custody,
  producer identities, and provider artifact coordinates.
- the fixed-point contract owns all generated consequences and rejects
  non-convergence or hand-maintained drift.

### Contracts to producers

1. Reconciler emits clean candidate bytes and, when required, definition and
   authority commits as one governed operation.
2. PR producers emit authenticated grouped evidence for the exact candidate.
3. Exact-main admission and producers emit truth for the exact merged subject.
4. Trusted finalizer authenticates the complete same-admission inventory.
5. Status publisher emits only the certification context matching the scoped
   proposition.
6. Release authorizer selects current terminal exact-main certification.
7. Hosted builder emits untrusted candidate assets bound to authorization.
8. Independent verifier executes the closed wheelhouse and emits runtime proof.
9. Trusted collector reauthenticates all upstream identities and emits the sole
   release receipt.
10. Trusted publisher authenticates receipt, assets, attestations, tag state,
    and its own role before the first provider mutation.

### Producers to consumers

- PR certification is consumed only by protected merge eligibility.
- Exact-main bounded certification is consumed only by declared successor
  workitem eligibility.
- Exact-main terminal phase certification is consumed by release authorization.
- Controller artifacts are consumed only by exact-bound bootstrap/probe and
  confirmation; candidate code cannot install itself.
- Build output is consumed by verifier and collector only through exact
  authorization and manifests.
- Release receipt is consumed by publisher only through provider-authenticated
  artifact identity.
- Immutable release custody is consumed by installer/upgrade verification and
  adopter qualification; a local wheel path is not release custody.

## Canonical DAG

```text
intent
  -> reconcile(definition -> authority -> fixed point)
  -> PR preflight -> controller compatibility -> PR evidence -> PR certification
  -> protected merge
  -> exact-main admission
     -> [pending rotation: build N+1 -> bootstrap -> probe -> confirm -> normalize]
     -> exact-main evidence -> scoped truth -> trusted finalizer -> status publisher
  -> terminal-phase certification
  -> release authorization -> hosted build -> independent verification
  -> trusted collection -> release receipt
  -> publication read-side validation -> create/reuse exact tag
  -> draft upload -> digest verification -> immutable publish
  -> credential retirement -> adopter qualification -> custody closeout
```

No edge may be skipped because a later node appears green. A retry retains prior
evidence only when its consumer reauthenticates the original exact identity and
the retry contract explicitly permits a new attempt.

## Publication state machine

```text
RECEIPT_AUTHENTICATED
  -> ASSETS_ATTESTED
  -> TAG_ABSENT | TAG_EXACT | TAG_CONFLICT
TAG_ABSENT -> TAG_OBJECT_CREATED -> TAG_REFERENCE_CREATED -> TAG_EXACT
TAG_CONFLICT -> STOP
TAG_EXACT -> DRAFT_CREATED -> ASSETS_UPLOADED -> DIGESTS_EXACT
DIGESTS_EXACT -> IMMUTABLE_PUBLISHED -> CUSTODY_VERIFIED
```

An orphaned tag object has no reference authority and may be superseded by a
retry. A created tag reference is never force-updated or deleted. A retry must
reread and validate it. A draft or published release with unexpected identity
is conflict, not resumable absence.

## Prospective correction checklist

Every late correction records the following before its first push:

1. Enumerate every reachable state above for both current and proposed bytes.
2. Trace changed invariant -> primitive -> contract -> producer -> consumer.
3. Classify each downstream surface as canonical change, generated consequence,
   test-only, or inspected-no-impact.
4. Validate candidate preflight, installed-controller compatibility, PR evidence,
   certification, protected merge projection, exact-main applicability,
   controller lifecycle, scoped truth, finalization, publication, successor or
   release eligibility.
5. Exercise absent, exact, malformed, stale, wrong-subject, wrong-run,
   wrong-attempt, wrong-producer, conflicting, and retry states where applicable.
6. Run cheap structural budgets before semantic fan-out.
   This includes proving every tracked top-level source root is selected by the
   source-distribution manifest.
7. Reuse exact-input evidence where the applicability resolver proves it legal;
   otherwise state the changed binding that requires recomputation.
8. Require generated parity and a clean fixed point before provider execution.

The provider record remains the authority for actual run state. This document
prevents a correction from being evaluated only in the narrow state that first
exposed it.
